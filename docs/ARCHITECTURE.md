# 实现说明

2026-10-14 · 简单局域网版本。用户在设计稿完成后明确授权直接实现，不以未经真人试玩为由阻断此次开发；体验验收仍待实玩。

## 当前公屏新局：2026-10-19交谈版

用户已确认删减登记与答案选择题，优先让玩家互相追问。三人及两个四人配置使用`playMode: screen-led`、`flowVersion: 2`。完整玩法和推演见[CONVERSATION.md](CONVERSATION.md)。下文逐人搜证/对质、判断选项和自动应对提示只描述原版与旧存档，不再用于公屏新局。

- v2阶段：lobby → opening → dossier → search1 → search2 → vote → ended。进入两次讨论时自动公开本轮全部短物证，取消地点、次数与发言登记。
- 公屏阶段文案和新发现从`conversation.notes/beats`读取；物证只返回事实原文，不返回引导问题。`reasonOptions`在所有阶段为空，不把解答放进投票页面。
- 手机白名单只有本人身份、目标、三条亲历、可折叠的全文/开口方向/说谎边界；不返回逐阶段`focus`或按证据追加的`responseHints`。
- `screen_verify`仅允许主持凭证在讨论阶段核对已公开且带有`verification`的原物。未请求前服务器只返回`canVerify`，不传核验正文。已核验ID按房间持久化。
- `screen_votes`一次验证所有`{playerId,suspectId}`和`revealed: true`后原子写入。额外判断与证词字段被丢弃；按凶手多数判正确、错误或分票，不评分口头理由。
- 新建房间复制剧本版本；旧房间缺省v1，继续读取`story.v1.json`原稿。公共屏中止/结束后重开才切至当前稿和v2。六人故事继续使用原模式。
- 本次只新增玩法字段、内容版本和交谈分支，仍是单HTML、Node进程和本机JSON保存，没有新框架或运行依赖。

## 一个网页，一个进程

Node.js 22启动一个HTTP服务，监听`0.0.0.0:3210`。`web/index.html`同时承担首页、公共屏、手机和单窗口试玩，不需要编译。服务端只有二维码一个运行依赖。

浏览器通过POST发送操作，通过SSE接收自己的最新快照；断线自动重连。每个请求均校验凭证、阶段和参数。公共屏不占玩家席位。六人模式保持手机个人操作；三人和四人模式由公共屏登记口头调查、录入已经收齐并揭开的纸票。

## 文件职责

- `server.mjs`：HTTP路由、受限文件输出、凭证认证、连接在线状态、二维码、房间保存与清理。
- `engine.mjs`：独立的阶段与规则函数，处理角色分配、搜证、公开、提问、补查、全员完成、提示一致确认、投票及结果。
- `stories.mjs`：从`stories/*/story.json`读取和校验可信的本地内容，提供白名单摘要。
- `story.json`：所有人物、私人经历、物证、开场、答案和复盘；不依赖某个故事名称写死规则。

## 权限与投影

创建公共屏返回主持凭证；加入返回仅属于该玩家的随机凭证。两者均为256位随机值，浏览器存储按房间与用途隔离。扫码地址只含房间码，没有凭证。

服务器每次按凭证生成投影，不发送原始room或故事对象。六人及旧局的`classic`模式：

- public：当前阶段、公开身份、完成/在线状态、已公开证据、问题与说法。结束前没有答案、投票内容、角色秘密或完整时间线。
- me：仅此人档案、已取得的物证、私人关联提示及自己的选票。
- ended：统一揭晓答案、全部角色、选票、证词与复盘。

公共屏的me始终为空。故事原文、源码、存档和测试文件没有静态下载路由。人物输入和故事文案输出时转义HTML。

2026-10-18新增三人本`screen-led`模式。公共屏持有共同导读、关系、物证和结局；手机采用独立白名单投影，只含基础阶段、本人昵称、发放后的`actionCard`及已公开证据对应的`responseHints`，不返回共同故事、其他角色档案、公共物证、判断选项和完整复盘。`cardsReleased`持久化，只有公共屏从开场推进至身份阶段才置为真；开场中止也不会意外解锁身份。应对方向由服务器按`room.published`筛选，不传送整套未来提示。

## 本局昵称与角色身份

2026-10-17按用户要求，故事内的玩家人物直接使用入席昵称，公开身份（如修复师、经纪人）继续由角色决定。作者原名只保留在角色定义中方便编辑；叙事内使用`{{role:角色id}}`引用玩家人物。NPC姓名固定，不随入席昵称改变。

`stories.mjs`验证所有角色引用；`personalizeStory`按本局`roleId→nickname`生成独立内容副本，`engine.mjs`随后按凭证投影。开场、私人档案、物证及提示、系统提问、判断选项、结局与复盘使用同一份映射。角色ID、凶手身份和答案不因名字改变。昵称只作为纯文本替入，不再次解析其中的模板；玩家自己写的说法不做替换。各房间不修改共享原始故事，重开按新角色分配重新绑定，恢复存档仍使用原昵称和角色ID。

旧存档的结局和提问在投影时由对应角色、证据重新生成展示文案，无需迁移房间凭证。新增故事应使用角色引用，避免在正文写死作者姓名。

## 推进与并发

阶段为lobby→dossier→opening→search1→search2→confrontation→vote→ended，另有明确的aborted状态。

上述为`classic`。三人、四人新局使用lobby→opening→dossier→search1→search2→confrontation→vote→ended；`playMode`按创建时剧本配置存入房间，缺省为旧模式，运行中不根据新版故事自动改变阶段。重开时才采纳当前剧本模式。

阶段ID每次推进与重开递增；客户端提交当前界面的ID，不自动把旧操作升级到新阶段。服务端拒绝陈旧消息，重复搜索同处不重复发卡，重复公开不清空完成标记。

每轮每人一次搜证；未搜证不能完成。新证据公开或新提示揭示，清除全员本阶段完成标记。全员完成后归档已查物证再进入下一阶段。对质中补查不限额，每人发言或放弃后才能确认指认。

票可在收齐前修改，全收齐立即冻结并裁决。公共屏在此前只知道谁已提交。多数门槛为人数一半向下取整再加一，凶手与关键判断按故事答案计算。

`screen-led`仅主持凭证可执行`screen_next`、`screen_search`、`screen_supplement`、`screen_speak`、`screen_hint`、`screen_votes`；手机游戏操作一律拒绝。每轮每人一次登记，物证立即公开，登记齐且口头讨论完成后手动推进；对质逐人登记发言或放弃，补查不限。公共提示由操作者确认全桌口头同意后展开。`screen_votes`一次提交`revealed: true`和全体`{playerId,suspectId,reasonId}`，校验人数、唯一玩家及合法选项后才统一写入、结算，强制`testify: false`；不完整票据不会留下部分选票。程序无法验证真实纸票是否收齐，这一步由全桌遵守规则。

## 保存与恢复

每次有效变更同步写临时JSON，再重命名替换存档，文件权限为600。保存失败则恢复变更前状态并返回错误，不把未保存的状态广播给玩家。在线状态来自实时连接，不持久化；刷新或服务重启使用原凭证恢复。

恢复存档要求对应故事仍在；缺失或格式错误时明确启动失败，不悄悄覆盖。游戏期间不要修改现有故事。原始存档包含秘密和凭证，不可作为公共复盘分享。

全知复盘只在结束后下载，内容为已揭晓公共结果，不含凭证。48小时没有操作且没有连接的房间清理。

公共屏模式只在公共屏提供复盘。纸票录入草稿按房间码与阶段ID保存在公共屏浏览器`sessionStorage`，SSE重绘及刷新可恢复，关闭会话后可能丢失；正式房间存档只保存核对提交后的完整选票。A4打印样式按故事人数输出空选票，不打印私人卡、答案或录入值。

## 单窗口试玩

只能从回环地址创建；独立房间标记demo，拒绝真人加入。创建者得到与所选故事人数一致的独立玩家凭证，网页用这些正常凭证串行完成其他席位，没有后端跳阶段或全知代判接口。试玩有持续显示的剧透提示。

三人、四人试玩不提供“其余玩家完成”助手，全部操作在左侧公共屏执行；右侧切换只读私卡。试玩公共区使用主持凭证，私人区使用选中玩家凭证分别读取；公共屏SSE触发刷新。正式手机不具备这个组合视图。

## 当前扩展边界

故事支持3～8名角色、一名凶手、两轮调查，每个地点每轮恰有一份物证。平台读取多个故事；不同机制需修改engine及相关测试。现有《雪夜来信》为六人，《闭馆之后》为三人，《末班渡口》与《人鱼·暗渠来信》为四人，均为独立案件，不能通过删减同案角色改变人数。三人多数为两票，四人多数为三票；四人二比二或二比一比一不形成多数，仍须所有选票收齐后统一结算。公共屏文案、关系栏、纸票数量按剧本人数渲染。

存档不是跨设备登录，浏览器凭证遗失后不能自动找回。适用于信任服务器电脑的局域网聚会，不包含公网部署、用户账号或云端同步。
