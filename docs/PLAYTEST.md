# 真人实玩记录：第七位访客

目的：验证六个朋友是否真的需要交流、隐瞒和承担代价。自动同伴与浏览器测试只能证明流程正确，不算这份验收。

## 准备与进行

1. 分别完成一场4人、一场6人面对面实玩。一台电脑运行 `pnpm dev`，玩家用真实手机扫码加入；电脑不占玩家名额。
2. 主持开启现场声音，先确认字幕与画面可读。所有人普通人开局，不提前分配卧底，不提前讲解全部事件答案。
3. 主持只解释当前困境和操作，不替大家选行动；允许坦白私人指令，也允许撒谎或拒绝。大家可以自主看过后点已读，没有倒计时。
4. 结局先谈各自感受，再看完整因果回放，避免把结局才知道的真相当作当时已知。
5. 电脑点击“保存本局故事回放”，保留JSON；文件只含已揭晓的故事，不含重连凭证。它不是中途存档，也不是带随机种子的可执行复现文件。

## 本轮特别要回答的三个问题

- 第一幕为什么有人愿意签名？当前签名主要增加风险，如果只有“不知道会怎样所以试试”，重复游玩的动机可能不足。
- 异变后为什么有人愿意传播？当前没有直接的个人收益，可能只能依赖玩家自愿扮演恶意。需要验证是否应让“与异常合作”提供有代价的自保机会，而不是强制换阵营。
- 玩过一次的人能否直接指挥全桌照固定安全路线走？若如此，需要调整信息与代价的组合，不以新增按钮、背包和职业解决。

上述是从代码规则发现的设计风险，不是已经得到真人证实的结论；也不能据此宣称游戏性通过。先保留实际对话和选择，再决定是否改规则。

## 结束后每人各回答一句

1. 哪一幕最想跟别人谈条件，为什么？
2. 哪一幕完全不需要讨论，为什么？
3. 有没有一个你想做、但现有选项不允许表达的决定？

完成4人和6人记录后，再结合故事回放调整指令动机、代价和演出节奏。不要把“所有人都活着出来”当作唯一成功标准，也不要把“有人被感染”当作体验成功的证明。
