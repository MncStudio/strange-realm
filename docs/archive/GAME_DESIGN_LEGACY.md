# 诡境 StrangeRealm — 游戏设计档案

此文件用于持续记录玩法、剧本机制和实际测试结论。后续修改游戏，请先阅读本文件与现有实现。

## 1. 核心体验

4～6位朋友坐在一起，一台电脑作为服务器与公共主持屏。玩家用手机查看自己的秘密档案，现实中自由讨论、交易、说谎与结盟。主持电脑是公共信息展示端，不拥有查看他人秘密的权限，也不占玩家名额。

开局每个人明确知道身份、目标与特殊能力。共同生存需要合作，个人目标可能要求某种公共结局、物品归属或特定行动。系统记录真实状态，语言承诺不会自动改变状态，必须实际提交行动。

## 2. 第一版范围

只实现《第七位访客》。六位访客来到地图上不存在的旅馆，登记簿上却有第七个人。玩家需要在第七轮结束前打开出口或封住旅馆中的东西。

游戏是完整回合制，没有时间限制或自动推进。所有玩家提交后统一结算，停留在本轮因果报告和本人回执。开场、每轮结果及最后一轮的结局揭晓都必须由主持确认继续。主持不能跳过在线未提交者；对离线未提交者可明确补交剧本默认行为。

人数不足六人时从六个不同角色中抽取，保持每位玩家角色与目标唯一。随机种子控制角色、规则组合、事件及冲突优先级。同样种子和行动产生同样结果，发送行动的先后不决定优势。

## 3. 信息边界

公共信息：剧本简介、规则文本、回合、事件、世界资源、玩家健康/在线/准备/提交状态及公共后果。

私人信息：身份、目标、能力、物品、线索、提交的行动和行动结果。只有该玩家连接收到这些数据。公共屏在对局结束前也不能查看。

终局：所有角色、目标与判定原因揭晓；每轮行动、触发规则、物品变化和公共后果组成故事回放。结束前回放为空。

## 4. 引擎与剧本扩展

`packages/shared` 保存允许跨网络传输的类型。`packages/game-engine` 保存通用阶段管理、角色分配、行动收集、确定性结算与投影。`packages/scenarios` 保存服务端使用的本地JSON配置和规则模块。Web只读取服务端给出的剧本摘要，不能直接加载剧本JSON。

增加剧本应提供唯一ID、人数与时长、角色、物品、事件、行动、规则与结局，并注册规则模块。旅馆专属规则留在剧本包，不写到房间服务和页面中。平台按服务端剧本清单展示选择卡片。

## 5. 局域网与房间生命周期

一台Mac运行Node服务和Vue界面，其他设备连接同一局域网。二维码使用Mac的局域网IP。断线后保留重连席位，刷新通过浏览器每个标签页独立保存的token恢复原身份。游戏中离线玩家继续占位，等待重连或主持明确替其守候；大厅主动退出释放位置。

房间和游戏状态仅存于服务端内存。停止或重启服务器会丢失房间，第一版不提供持久化存档。所有玩家离开后房间按服务端生命周期清理。重新开局返回大厅、清除私人档案、重新准备并产生新种子。

## 6. 后续打磨方向

- 先观察六人面对面交流中的无聊时段、交易频率和个人目标胜率，再调整内容数量。
- 通过实玩校准世界资源、行动收益和冲突风险，特别关注离线默认行为与低人数难度。
- 为新剧本扩展特定状态与规则，不把所有叙事塞入随机事件池。
- 第二版可以加入主持音效、场景音景、更多线索组合、明确的双向交易确认及可选存档；首版不依赖AI裁决。
- 极简重连是设备持有token即拥有身份；未来若需要跨设备恢复，可增加私密恢复码，而非账号注册。

## 7. 《第七位访客》的实际机制

最多7轮；讨论、阅读均不限时。不能保证15～25分钟固定时长，由现场交流决定。每轮全员提交后进入结果页，不自动进入下一轮。取消旅馆钟表，使用第几轮表述。

世界初值：异常威胁2、电力3、封印0、出口0；上限分别12、6、6、8。每人生命3。主要离开路线为出口达到6且电力至少1，或封印达到4且出口至少4。异常威胁表示旅馆危险程度，不代表玩家惊慌；达到9会伤害仍在现场的玩家，12触发失控终局。共享生存与私人目标独立判定。

| 角色 | 私人目标的关键条件 | 核心谈判空间 |
| --- | --- | --- |
| 调查记者 | 3条不同线索，活着离开 | 相机与证据可换取保护，闪光会加异常威胁 |
| 失职医生 | 成功治疗受伤的其他玩家，活着离开 | 需要真实伤者与药物，别人可制造可控风险 |
| 夜班电工 | 2次有效修复，结局电力至少2，活着离开 | 修复公共资源，也可交换保险丝 |
| 通灵师 | 亲自镇灵或协同念诵、封印4、活到结局 | 至少两人念诵更有效；推动封印路径 |
| 失踪者继承人 | 查看登记簿、持铜钥匙、活着离开 | 钥匙使用不消耗，能借出也可能被偷 |
| 逃债赌徒 | 亲自破坏一次、持古币、活着离开 | 私人目标损害公共资源；古币可换出口帮助 |

21种行动：守候、守护、远程协助、赠予、秘密盗取、搜索、查看登记簿、监听、修复、点烛、治疗、镇灵、念诵、拍摄、看镜、回应铃声、访客交易、钥匙开门、强拆门锁、秘密破坏、尝试离开。

保护先于物品转移，赠予先于偷取，资源修复/仪式先于开门和破坏，逃离最后判定。相同优先级按种子生成的次序结算。赠予是单向操作，双方同轮赠予可以交换，也允许一方失信；首版没有系统担保的双向交易。

| 规则 | 实际执行的因果 |
| --- | --- |
| 无电的门 | 断电时钥匙无法推进出口，触碰会受伤 |
| 铃声需要见证 | 铃声事件至少两人回应才能推进出口；独自回应受伤 |
| 门后的呼吸 | 呼吸事件碰门增加伤害和异常威胁 |
| 双声仪式 | 至少两人同轮念诵推进封印；独自念诵只增加异常威胁 |
| 古币的契约 | 古币换帮助后，后续访客事件会追索签约者 |
| 短烛补光 | 烛光降低异常威胁，完全断电时还能补电 |
| 被涂改的名字 | 全局首次查看登记簿推进出口，后续仍可取线索 |
| 等待黎明的谎言 | 告示承诺等待获救，实际多数人守候时出口倒退、异常威胁上升 |
| 红镜吞影 | 红镜版本查看受伤；镜廊拍摄也有额外危险 |
| 蓝镜映路 | 蓝镜版本查看降低异常威胁，镜廊拍摄无额外伤害 |
| 失物追索 | 启用该规则时成功盗取会反噬盗取者 |

每局抽取红镜＋失物追索，或蓝镜＋无追索两个组合。前8条共用，其余根据本局旗标实际启用，并与公开告示一致。16个事件由轮次、电力、异常威胁、封印、出口和先前旗标筛选，再从合法候选中抽取；不存在只为讲故事而忽略状态的事件播放队列。

死亡/逃离不会剥夺参与：仍可守候稳定情绪、监听取线索或远程协助。私人目标按真实存活与逃离情况判定，不能靠协助恢复已失败的生存条件。

公共终局共4种：退房成功（正常出口）、无名黎明（封印路线）、旅馆的新住客（全灭/异常威胁失控/七轮结束无法离开）、不完整的退房（已有部分玩家逃离，剩余者失败）。共同成功要求全员存活；有人死亡时，其他玩家仍可能完成私人目标。已经离场的人不会因本轮之后发生的断电再次被困。

## 8. 实现与测试记录

- `pnpm install --frozen-lockfile`、`pnpm dev` 实际启动成功；本机与Mac局域网IP下的首页/API均能访问。
- `pnpm typecheck` 全部包与测试脚本通过，`pnpm build` 生成Web静态资源与服务端bundle。
- `pnpm test` 共62项通过（引擎/剧本28项、服务端输入34项）。覆盖全部规则类型、4结局、个人目标、物品/保护冲突、网络提交乱序、事件条件、投影隔离、超时、重开，以及使用不同默认动作和人数的最小测试剧本。
- `pnpm test:integration` 使用真实Colyseus客户端模拟主持＋6名玩家。验证六个不同角色/目标、主持无私人消息、公共快照无秘密字段、越权控制/非法参数/过期回合/重复提交拒绝、主持和玩家断线恢复、超时默认行为、完整失败对局与六人合作成功退房。还验证重开释放离线席位、旧token拒绝、替补加入、全员退出后房间销毁。
- `pnpm test:browser` 使用真实Chrome页面模拟主持＋4个独立手机尺寸上下文，完成创建/二维码/准备/分配/独立行动/7轮结局/身份揭晓/重开，并验证主持与玩家刷新恢复；无浏览器错误或横向溢出。1600×900公共屏、390×844私人档案和结局截图在 `test-results/`。

测试中修复的问题包括：旧Room对象重复leave导致验收脚本悬挂、离线重开旧token恢复至已移除角色、继承人借用他人调查完成任务、全员离场后事件断电错误改判、前端错误展示离场目标、缺少favicon产生404、大屏与手机行动列表的操作布局。

## 9. 单人试玩与场景呈现（2026-10-13）

`pnpm demo` 现采用单窗口流程：公共剧情和本人手机界面并排显示，另外3位同伴在后台自动合作；六人配置也不增加页面。主按钮依次启动、进入回合、确认推荐选择、读完结果继续、查看结局、重开。玩家手动提交后，同伴自动完成剩余行动。取消自动走完按钮；结果页必须主动确认，没有倒计时。

每个虚拟玩家拥有独立Colyseus连接、Pinia实例和sessionStorage命名空间；只向该玩家对应连接发送私人投影。公共组件注入主持会话，仅本人手机组件注入本人会话；不在终局前展示同伴秘密。规则引擎与权限校验保持正常执行。测试页仅在开发试玩环境注册，生产构建与普通开发入口不提供该路由。

`pnpm check` 汇总类型检查、62条单元测试、构建和六人协议测试；`pnpm test:browser` 验证图片加载、动效开关与偏好保存、系统减少动态设置以及四人完整浏览器闭环。

《第七位访客》新增3张环境图：雾夜旅馆、镜廊、前台登记簿。服务端规则不引用美术资源，前端通过独立art.json按公开事件ID映射图片。动效是表现层的慢速推进、雾气、扫描线、场景淡入与资源反馈，不改变判定与推进节奏。用户可关闭，且尊重系统减少动态偏好。原始素材、文件路径和内置image_gen最终提示词见 `ART_ASSETS.md`。

自动合作仅用于检查技术流程；私人目标博弈、交易与谎言仍需要朋友面对面实玩。

本次验证：4人有窗口试玩的c合作与q清理实际通过；6人无窗口试玩检查通过。62项单测、类型检查、构建、六人协议回归以及四人浏览器闭环均通过。浏览器额外验证图片实际加载、动效偏好刷新保存、减少动态设置，以及场景切换在3秒内完成；修复持续背景动画被Vue误用作28秒过渡时长的问题。


单窗口更新验证：四人和六人仅一个浏览器页面完成整局、重开与刷新恢复；本人手动提交后自动同伴正确提交，公共画面未展示本人身份。单窗口版替代早期多窗口/终端c命令方式。

## 10. 无计时与入门引导更新（2026-10-13）

实玩反馈：选择过多，不知道当前要解决什么；“惊惧”像凭空变化的情绪，“封印”缺少解释；倒计时和自动推进使玩家来不及理解后果。

采用以下流程：开场阅读 → 主持进入第一轮 → 每人独立提交一个行动 → 全员提交统一结算 → 公共因果报告＋本人回执 → 主持读完确认继续。最后一轮也先停在报告，确认后才揭晓身份、个人胜负与故事回放。任意等待都不跳阶段，不向在线未提交者补默认行动。

公共报告逐项列出异常威胁、电力、封印和出口的前后值，以及每次实际增减的来源，包括行动效果、误导规则与事件余波。原因不标出谁提交秘密行动；本人伤害和行动成败仅在手机回执解释，全部行为在终局回放揭晓。

行动页默认最多4个建议，说明当前问题、本人目标和建议理由；更多行动折叠。共同路线明确为出口6＋电力1。封印是仪式压制访客的备用路线，封印4＋出口4也可离开；不要求第一局同时追求两条路线。建议根据局势和角色动态更新，两人仪式与铃声见证必须先约同伴，不由系统代替讨论。

离线处理：不自动补交；主持可选择“替离线玩家守候”，只填未提交的离线者。玩家重连保留已经提交的选择。主持断线时全员已提交仍会结算，但结果停留等待主持恢复；主持在游戏中长期离线不会自动结束对局，需要恢复该浏览器会话。

验收结果：类型检查、构建、64项单元测试通过（引擎/剧本30项，服务端输入34项）；六人真实WebSocket测试完成失败与全员退房两条路线；四个模拟手机浏览器完成逐轮选择、公共和私人结果、最后一轮确认揭密、重开；四人和六人单窗口试玩完成逐轮确认、结局、重开、刷新恢复。检查无浏览器错误与横向溢出，查看了主持和手机结果截图。

测试覆盖无论等待多久均不推进、少一人不结算、最终报告确认前不揭密、离线补交权限与重连、报告增减与实际数值一致、六角色最多4个合法建议。还修正测试驱动在客户端关闭后立即重连、早于服务端登记重连票的竞争：测试使用与界面相同的有限重试，不改变权限或重连时限。

结果页手机同时显示本人回执与公共因果报告，切换阶段后滚动回顶部。结果的下一步建议只根据已结算后的局势，不误把本轮已结束的铃声或呼吸事件当成下一轮要求。后续剧本即使未提供逐项原因，通用报告也会标明实际未解释增减，避免把变化误写成“没有改变”。

默认试玩端口被旧窗口占用时，验收使用独立端口5195/2599；没有中断旧窗口。修改后应停止旧试玩并重新运行pnpm demo，服务端内存房间不会跨重启保留。实体手机和朋友面对面讨论、私人任务胜率与推荐动作的实玩效果仍需进一步验证。
